# Журнал змін статусів замовлень

Журнал починається після міграції `2026_09_07_130000_create_order_status_changes_table`. Старі події не вигадуються і не додаються заднім числом.

У картці замовлення блок «Історія статусів» показує час за Києвом, попередній і новий статус, користувача або автоматичний процес, джерело та причину. Дані завантажуються лише після відкриття блоку, по 20 записів. Доступ мають власник та оператор, як до самої картки.

## Гарантії запису

`Order` через `RecordsOrderStatusChanges::performUpdate()` перехоплює зміни `status` та `status_id`, зокрема `saveQuietly()`. Перед оновленням виконується `lockForUpdate()` на тому самому зʼєднанні. Попередній стан читається з бази, а не із застарілого екземпляра моделі. Оновлення й запис журналу входять в одну транзакцію: якщо журнал не зберігся, зміна статусу відкочується. Повторне збереження тих самих значень і зміни інших полів не створюють подій.

Для автоматичних процесів використовуйте:

```php
$order->updateWithStatusAudit(
    ['status' => $status->code, 'status_id' => $status->id],
    'nova_poshta_sync',
    'Статус оновлено за результатом автоматичної перевірки НП',
    ['ttn' => $ttn, 'np_response' => $row],
);
```

Контекст одноразовий, очищується і після помилки. Для НП зберігаються лише ТТН та поля `StatusCode`, `Status`, `StatusDescription` з обмеженням довжини. Довільні поля відповіді, ключі API та контактні реквізити не копіюються. Автоматична синхронізація, автоматичне розблокування й фіскалізація записуються як системні процеси; ручна перевірка НП містить користувача.

Журнал зберігає знімки назв статусів та імені користувача. Видалення замовлення, користувача чи статусу не видаляє відповідні записи журналу. Через API доступне лише читання.

## Правила для подальших змін

- Статуси задаються перед `save()` / `update()`, не всередині `updating` чи `saved` observers.
- Не змінюйте бізнес-статуси через масові `Order::where(...)->update(...)`, `DB::table(...)`, raw SQL або `upsert`: вони обходять модель і журнал. Для пакетної зміни перебирайте моделі через `chunkById` та `updateWithStatusAudit()`.
- Службове виправлення через SQL потребує окремого знімка до/після та причини, як під час інциденту 7 вересня. Журнал застосунку не замінює резервні копії й MySQL binlog.
- Мережеві запити виконуються до транзакції запису, щоб не тримати блокування під час очікування НП.
- Не змінюйте і не очищайте журнал під час звичайного редагування замовлень.

Індекси `(order_id, id)` і `(source, occurred_at)` підтримують читання історії та пошук інцидентів без повного сканування таблиці.
