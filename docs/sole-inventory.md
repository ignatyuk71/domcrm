# Запас підошви: отримані партії та прогноз

Сторінка `/sole-inventory`, меню «Аналітика → Запас підошви», доступ лише власнику. Спільна навігація має вкладки «Продажі» та «Запас підошви»; пункт меню відкриває останню відвідану вкладку в поточній сесії, типово — продажі. Старі адреси сторінок і API не змінені. Структура взята за прикладом сторінки магазину, але дані й відправлення — **тільки CRM**. Зовнішні API не викликаються.

## Дії користувача

1. «Додати партію»: дата фактичного приїзду та отримана кількість **пар** кожного розміру. Якщо певного розміру не було — 0. Щонайменше один розмір має додатну кількість. Майбутні поставки не збільшують запас.
2. У «Прогнозі» за бажанням указати повний термін нової поставки (виробництво + доставка з Китаю), додатковий запас часу та період середньої витрати.
3. Наступна отримана партія додається тією самою дією. Помилку дати/кількості можна виправити через «Редагувати» у списку партій; зміни аудіюються.

**Поточний залишок, собівартість і грошову суму користувач не вводить.** Не потрібне попереднє налаштування чи створення початкового залишку.

Категорії: «Домашні капці Halluci (хутряні)» та «Капці для вулиці (хутряні)». Ідентифікатори категорій не зашиті в код. Категорії та розміри рахуються окремо. Картки показують отримано / витрачено / залишок, дні й приблизні місяці до закінчення та до замовлення. Таблиця окремих останніх замовлень видалена; залишена зведена витрата за місяцями.

## Формула

Залишок = сума всіх отриманих партій − відправлені пари від дати найпершого приїзду включно. Додавання пізнішої партії **не скидає** дату відліку і не списує відправлення повторно. Додавання старішої партії або редагування її дати автоматично змінює початок розрахунку. Від’ємний залишок не приховується.

Витрата — `order_items.qty`; категорія — пов'язаний товар CRM; розмір — знімок позиції або відповідний варіант, якщо знімок порожній. Варіанти `36/37`, `36-37-24 см` тощо об’єднуються; помилковий `42/23` не вгадується. Невідомі розміри показуються у попередженнях.

Дата витрати — найраніший доказ відправлення в історії доставки/статусів CRM. Сама створена ТТН, пакування чи переадресація 104 не є відправленням. Якщо залишився лише пізніший результат, дата приблизна. Резерв — `status_changed_at` відправленого, прибулого, отриманого чи повернутого замовлення; `orders.created_at` ніколи не підставляється. Недатовані записи не списуються й показуються для перевірки.

Одна ТТН перевізника — одне замовлення (найстаріший ID з доказом відправлення серед цільових категорій), зі всіма його позиціями. Без ТТН рахуємо за замовленням. Пізніший статус повернення/скасування не відновлює сировину.

## Прогноз

Типово середня витрата рахується за всі **повні календарні дні від першої отриманої партії**, як у прикладі сайту. Можна вибрати 30/60/90 останніх днів, але не раніше першої партії. Це впливає лише на прогноз, не на залишок чи таблицю загальної витрати. Сьогодні зменшує залишок, але не входить до середнього темпу. Якщо перша партія приїхала сьогодні, прогноз чекає першого повного дня.

- Темп = відправлені пари за період / кількість календарних днів.
- Днів запасу = ціла частина залишку / темпу; місяці — наближено, 30,44 дня.
- Замовити до = прогноз закінчення − термін поставки − додатковий резерв.
- Термін поставки типово невідомий, додатковий резерв — 0. Без терміну рахується тривалість запасу, але не дата закупівлі.
- За нульового темпу дата не прогнозується. Розмір, який ніколи не надходив і не витрачався, не генерує хибного попередження «замовляти зараз».

Це приблизна оцінка, не виробничий облік: сезонність, пошиття наперед, брак та повторні відправлення готових повернень можуть впливати на точність. Зміна старих позицій/категорій товарів теж змінює звіт. Записи без пов’язаного товару не класифікуються за назвою.

## Збереження та сумісність

`sole_inventory_batches` містить прибуття, кількості розмірів, примітку, автора, версію й унікальний ключ запиту. Створення партії автоматично створює план, якщо його немає. Унікальний `request_key` захищає від повторної відправки одного запиту; інший вміст із тим самим ключем дає 409. Редагування партій і параметрів має optimistic locking та блокування категорії. Історія змін зберігається в `sole_inventory_plan_revisions`.

Старі `opening_date`, `opening_balances` і рухи не видаляються. Наявні плани мають `basis=legacy`, їхня попередня база враховується окремо, з явною позначкою, не видається за закупівлю. Нові плани мають `basis=receipts`; старі поля не задають для них ні запасу, ні дати відліку. Спроба змінити залишок через стару форму відхиляється з проханням оновити сторінку. GET не створює даних; міграція не імпортує запаси з магазину.
