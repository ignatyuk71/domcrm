# Запас підошви у CRM

Сторінка `/sole-inventory`, пункт «Склад → Запас підошви». Перегляд і зміни доступні лише власнику. Магазин dream-v-doma не є джерелом даних, зовнішніх API-запитів цей модуль не виконує.

## Початкове налаштування

- Категорії: «Домашні капці Halluci (хутряні)» та «Капці для вулиці (хутряні)» з довідника CRM. Ідентифікатори не зашиті в код.
- Початкові залишки вводяться в **парах**, на початок зазначеної дати за часовим поясом застосунку (Europe/Kyiv). `null` означає «не внесено», `0` — відсутній запас.
- Термін поставки включає виробництво й доставку; за замовчуванням невідомий. Резерв часу — редагований початковий параметр 14 днів. Період темпу — 30/60/90 повних днів до сьогодні.
- Після першого руху дату базового залишку змінювати не можна. Помилки рухів виправляються підписаними коригуваннями з обов'язковою причиною. Прибутковуються лише отримані, не очікувані партії.

## Розрахунок

Залишок = база + надходження + підписані коригування − відправлені пари від базової дати включно.

Кількість береться з `order_items.qty`, категорія — з пов'язаного `products.category_id`, розмір — зі знімка позиції або відповідного варіанта, якщо знімок порожній. Розміри з довжиною устілки та різними роздільниками нормалізуються. Помилковий `42/23` не стає `42/43` автоматично.

Дата — найраніша збережена ознака відправлення в історії доставки чи статусів CRM. Коди створеної ТТН й перенаправлення 104 самі по собі не підтверджують відправлення. Якщо є лише пізніший результат, дата позначається приблизною; останній резервний варіант — `orders.status_changed_at` для відправленого, прибулого, отриманого чи повернутого замовлення. `orders.created_at` не використовується. Без дати позиції не списуються, замовлення потрапляє у попередження.

Поточне скасування/повернення не скасовує вже підтверджене відправлення. Одна ТТН перевізника враховується один раз, за найстарішим ID замовлення з доказом відправлення серед відповідних категорій. Усі товарні позиції цього замовлення додаються. Дублі показуються для перевірки; без ТТН рахуємо за замовленням.

Темп = кількість відправлених за період пар / календарні дні періоду. Сьогодні враховується у залишку, але не в середньому темпі. Днів запасу = ціла частина залишку / темпу. Замовити до = дата закінчення − термін поставки − резерв. Нульовий темп не дає дати прогнозу; відсутні залишки/термін поставки не замінюються вигаданими числами. Негативний залишок не приховується.

## Межі точності

Це оперативний прогноз витрати за відправленнями, а не виробничий журнал. Зміна старих позицій/категорії товару впливає на розрахунок. Заготовки у виробництві, брак, повторний продаж готового повернення потребують інвентаризації та коригування. Повернення саме по собі не відновлює сировину. Неприв'язані до товару позиції не класифікуються за назвою. Неповна історія й сезонність можуть викривляти темп.

## Захист та перевірки

Плани мають optimistic locking (`version`); запис під блокуванням категорії захищає і перше створення. Усі версії налаштувань з автором зберігаються в `sole_inventory_plan_revisions`. Рухи мають унікальний `request_key` для безпечного повторення мережевого запиту; той самий ключ з іншим вмістом дає 409. Початкові залишки та рухи не створюються при GET. Міграція не додає вигаданих запасів.
