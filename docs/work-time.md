# Табель робочого часу

Сторінка `/work-time`, пункт меню «Табель». Поточний місяць і рік обираються автоматично; доступні попередні роки. Працівники табеля не є користувачами CRM і не отримують доступу до системи.

## Доступ і конфіденційність

- Власник і активний оператор: місячний табель, введення годин, примітки за день.
- Лише власник: створення/редагування/архівація працівників, читання та зміна нарахувань.
- Пакувальник, деактивований користувач і гість доступу не мають.
- Загальний API табеля не читає зарплатну таблицю і не повертає ставки чи суми. Зарплатні API захищені серверним `role:owner`, відповіді мають `Cache-Control: private, no-store`. Усі записи проходять session auth та CSRF.
- Початкових працівників, ставок і зарплат немає: приватні дані вводить власник у CRM. У репозиторії лише синтетичні тестові приклади.

## Години

Рядки — працівники, колонки — календарні дні. Вихідні виділені, але редагуються. Порожнє поле дає нуль у сумі, проте в базі відрізняється від явно введеного `0`. Дозволено 0–24 години на день з точністю до 0,01 години, з крапкою або комою.

Введення зберігається після 600 мс паузи або виходу з поля. `Tab` переходить до наступної клітинки, `Enter` — до наступного працівника в тому самому дні. Ім’я — звичайний текст. Табель призначений тільки для введення: на сторінці немає додавання, редагування чи видалення працівників, модальних форм або зарплатних налаштувань, навіть для власника. Працівники, примітки й збережені нарахування не видаляються.

Результати дій відображаються через спільний `Toast.vue` та `useToast.js`: успіх зникає через 3,5 секунди; помилки лишаються до закриття/виправлення і містять працівника та дату. Є повтор запиту або оновлення при конфлікті. Невиправлена помилка не перекривається успіхом іншої клітинки. Підсвічення поля та `aria-invalid` зберігаються; закритий toast можна відкрити іконкою помилок у панелі чи фокусом на проблемній клітинці. Перше завантаження не показує «Збережено». Відкидання чернеток при оновленні потребує явної дії у warning-toast; закриття/скасування не відкидає даних.

Кожна клітинка має версію. Конкурентна зміна повертає 409 і потребує оновлення; автоматичного перезапису чужих змін немає. Повтор однакового збереження після втрати відповіді ідемпотентний. Поки є помилки, текст залишається у формі, перехід між місяцями блокується; перед виходом зі сторінки браузер попереджає про незбережене.

У БД години зберігаються цілими сотими частками. Порожній запис зберігає версію, тому очищення клітинки не дозволяє старому запиту повернути видалені години. Архівація зберігає всю історію; нові дні після дати архівації недоступні. Керування архівацією більше не відображається у табелі.

## Нарахування

Зарплатна форма прибрана з табеля. Сторінка **Налаштування → Працівники та зарплата**, `/settings/work-payroll`, доступна лише власнику та має дві вкладки: «Нарахування за місяць» і «Працівники». Створення, редагування, архівація/відновлення та незворотне видалення працівників розташовані тут. Архів можна показати окремим перемикачем. Працівники виробництва не є користувачами CRM; пункт «Команда» для облікових записів залишається окремим.

Місячний звіт показує дні, години, ставку, зарплату, премію, відшкодування витрат, нараховано, виплачено й залишок. Натискання на ім’я або олівець відкриває форму нарахування. Для погодинного працівника можна вибрати ставку за годину або денну ставку за 8 годин; неповний день оплачується пропорційно годинам. Ставка належить конкретному місяцю, не переноситься автоматично й не змінює минулі місяці. Невказана ставка не дорівнює нульовій: суми такого рядка невідомі, загальні підсумки позначаються неповними. Кількість днів — кількість дат із додатними годинами, не еквівалент повних змін.

Інтерфейс звіту — компактна відомість у стилі Excel, без великих карток підсумків. Дві групи рядків: «За годинами» та «За виконану роботу»; підсумки внизу. Ставка, її одиниця, премія, витрати й загальна виплачена сума редагуються прямо в білих клітинках. Сірі розрахункові клітинки та години — тільки для читання; коригування і примітка доступні через олівець. `Tab` переходить між полями, `Enter`/`Shift+Enter` — вниз/вгору тієї ж колонки. Порожня ставка лишається невідомою, порожні премія/витрати/виплачене означають нуль.

Автозбереження після 600 мс паузи або виходу з поля використовує наявний owner-only API та таблицю `work_payroll_months`, без нової міграції чи копіювання даних. Запити одного працівника послідовні; введений під час запиту текст не затирається відповіддю. Після мережевої помилки повторюється той самий знімок і версія, а вже потім новіші значення. Помилки лишаються в toast і підсвічуються в рядку, успіх іншого рядка їх не перекриває. Конфлікт 409 не перезаписується; відкидання чернеток для оновлення потребує явного підтвердження і відбувається лише після успішного читання. Перехід між місяцями та відкриття керування працівниками спочатку зберігають чернетки; при помилці дія блокується. Перехід між вкладками не знищує стан таблиці. Кнопка «Зберегти зміни» додатково відправляє всю чергу, а `beforeunload` захищає незбережене. Підсумки завжди показують підтверджені сервером значення.

- Базова оплата за годинами = години × ставка; за денною ставкою = години ÷ 8 × ставка.
- Базова відрядна оплата = суми з нижньої таблиці табеля. Нові денні клітинки заміщають старі детальні роботи відповідного дня, без подвійного рахунку.
- Зарплата = базова оплата + коригування. Коригування допускає знак мінус і потребує пояснення.
- Нараховано = зарплата + премія + відшкодування витрат.
- Залишок = нараховано − виплачено; від’ємне значення означає переплату.

«Витрати» трактуються як відшкодування додатково до зарплати. Грошові значення зберігаються у копійках, базова оплата округлюється один раз. Сервер сам обчислює суми, надіслані клієнтом підсумки заборонені. Після збереження використовуються актуальні дані табеля. Поки нового місячного нарахування немає, виплачене за відрядними роботами береться зі старих детальних записів; після збереження власник вказує **повну суму виплаченого за місяць**, яка заміщає старий агрегат, а не додається до нього.

Звіт читається фіксованою кількістю запитів у транзакції, без N+1. Збереження нарахувань використовує версії, блокування працівника, ідемпотентний повтор та аудит. Міграція `2026_09_19_090000_extend_monthly_work_payroll` додає поля до наявної зарплатної таблиці, не змінюючи старих записів. Початкових приватних зарплат не імпортуємо. Форми захищені від випадкового виходу з чернеткою; інформаційні події показуються через toast, зокрема всередині модального вікна.

Перевірки: `php artisan test --filter=WorkPayrollSettingsTest`, `npm test -- resources/js/crm/pages/settings/SettingsWorkPayrollPage.spec.js`.

Це внутрішній розрахунок, без податків, лікарняних, відпускних і юридичного розрахунку зарплати. «Виплачено» — ручна загальна сума за місяць, не переказ грошей і не касова операція. Нарахування не додаються автоматично до калькулятора собівартості чи фінансів. Закриття місяця та реєстр окремих виплат не входять у цю версію.

## Відрядні роботи

При створенні працівника власник обирає «Погодинна» або «За виконану роботу». Існуючі працівники залишаються погодинними. Тип надалі не змінюється, щоб не змішувати історію. Відрядні працівники не потрапляють у сітку годин; сервер також забороняє їм години та погодинні нарахування.

Під таблицею годин розташована друга календарна таблиця **«За виконану роботу»**: працівники в рядках, дати в колонках, підсумок за місяць праворуч. Один вибір місяця/року керує обома таблицями. Власник вводить загальну домовлену суму за конкретний день через іконку в клітинці. Наприклад, 600 грн за 9-те та 300 грн за 20-те дають 900 грн за місяць. Кількість і розцінки вводити не потрібно. Порожня клітинка рахується як нуль, але відрізняється в БД від явно введеного нуля. Це **нарахована сума за роботу, не факт виплати**.

У клітинці сума — лише текст, під нею постійно видима іконка, зокрема в порожні дні. Прямого введення суми в таблиці немає. Іконка відкриває компактне віконце шириною до 320 px із сумою та необов’язковим полем «За що нараховано» (два рядки, до 500 символів). При наведенні на суму чи іконку підказка показує, наприклад, «34 грн — Нарізання поролону». Заповнені пояснення позначені зеленою іконкою. Тут редагується лише денне нарахування, не працівник чи його ставка. Зміни відправляються кнопкою «Зберегти», а «Скасувати» відкидає лише локальні правки; вже відправлена невдала спроба лишається в черзі табеля для повтору. Повторне відкриття форми саме по собі нічого не записує. Escape, клік поза вікном і зміна періоду не стирають локальну чернетку. Помилки — у toast, поля та іконка підсвічуються. До завершення запиту форма заблокована. Сума в таблиці та підсумки показують лише підтверджені сервером значення. Погодинна таблиця працює як раніше, з прямим введенням годин.

Для нарахувань використовуємо наявну чергу записів із повтором після мережевої помилки та версіями для конкурентного редагування. Перехід між місяцями спершу завершує черги **обох** таблиць, при помилці перехід блокується. Грошові клітинки зберігаються цілими копійками у `work_piecework_days`, пояснення — у nullable `note`; унікальний ключ — працівник + дата, зміни аудіюються у `work_time_revisions` з типом `piecework_day`. Сума та пояснення змінюються атомарно під спільною версією; повтор того самого запиту не додає ревізій. Омитий `note` не очищує наявного пояснення, явний `null` — очищує. Міграція `2026_09_20_120000_add_note_to_work_piecework_days` лише додає поле, без зміни сум. Доступ до сум і пояснень лишається лише у власника; операторський API годин не повертає ці записи.

Попередні детальні записи `work_piecework_entries` не видаляються. Поки день не редагували в новій таблиці, він показує суму старих нарахувань за цей день, а версія дорівнює сумі версій записів. Після редагування клітинка стає **повним підсумком дня** й заміщає старий агрегат у відображенні, а не додається до нього. Навіть очищення лишає версійну клітинку, щоб старі суми не з'явилися повторно. Після такого редагування старий API не дозволяє додавати/переносити/змінювати детальні роботи цього дня. Старі відомості про виплати й описи зберігаються без змін. GET нічого не створює. Міграція лише додає нову таблицю, не переписує дані.

Версія старого агрегату використовує суму версій **усіх** детальних робіт цього працівника, незалежно від дня: вона не зменшується при перенесенні роботи між датами. Сума дня й ця версія читаються одним SQL-запитом. Порожній день без старих записів має версію 0.

Немає переказів, касових операцій чи автоматичного списання коштів. Архівовані працівники з історією залишаються у відповідному місяці. Нових демонстраційних нарахувань немає. Перевірки: `php artisan test --filter=PieceworkDayTest`, `npm test -- resources/js/crm/pages/work-time/WorkTimePage.spec.js`.

## Технічні перевірки табеля

Owner-only API повного видалення використовується на сторінці налаштувань; кошика в табелі немає. API видаляє всі місяці: години, зарплатні нарахування, старі відрядні роботи, денні суми та їхні ревізії. Інші працівники й облікові записи CRM не змінюються. Залишається лише технічний запис `employee_deleted` (ID, автор, час, без персональних даних чи сум). Це не архівація; відновлення через CRM відсутнє. Сервер перевіряє роль власника, явне підтвердження та версію працівника; операція атомарна під тим самим блокуванням працівника, що й записи годин/сум. Повтор DELETE безпечний. Інтерфейс вимагає модальне підтвердження із назвою працівника; початковий фокус — на скасуванні. Перевірка: `php artisan test --filter=WorkEmployeeDeletionTest`.

`work_employees`, `work_time_entries`, `work_payroll_months`, `work_time_revisions`. Зміни атомарні; блокування рядка працівника серіалізує записи його днів/нарахувань. Індекси за датою та унікальні ключі працівник+дата/місяць. Кожна фактична зміна має історію до/після, автора і час. Журнал фінансових змін не віддається оператору.

Перевірки: `php artisan test --filter=WorkTimeTest`, `npm test -- resources/js/crm/pages/work-time/WorkTimePage.spec.js`. Міграція лише створює нові таблиці, не змінює замовлення, залишки, існуючі категорії чи собівартість.
