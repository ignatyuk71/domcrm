# NovaPay: поточний етап

Сторінка `/finance/novapay` та всі її API доступні лише активному власнику. Реальні рахунки підключаються через логін бізнес-кабінету, Refresh Token і відкритий сертифікат API. Токени й сертифікат зберігаються зашифрованими ключем Laravel; ключ `APP_KEY` потрібно зберігати між релізами. Тестові підключення та демонстраційні дані на сервер не переносяться.

Баланс отримується окремо від виписки: доступний залишок не залежить від обраного періоду. Помилка оновлення зберігає попереднє значення й час його отримання. Суми обчислюються в цілих копійках.

Імпорт операцій вмикається через `NOVAPAY_OPERATIONS_VERIFIED=true`. Контракт `GetPaymentsList` перевірено на реальному рахунку 16.10.2026: список містить надходження та списання поточного дня, а також повну вибірку за 1–16 жовтня. Запит використовує `date_type=0`, окремі дні та весь XML-відгук без клієнтського обрізання. На кожен день зберігається стан повноти імпорту.

ID операції береться з елемента `ID`, дата — з `DayDate`; у проведених списань `PayDate` може бути порожньою. Перевірений статус `Conducted` відповідає «Проведено». Невідомі статуси, дубльовані ID, некоректні дати, чужий рахунок і непідтверджена структура зупиняють увесь імпорт дня. Надходження без повного покриття періоду відображаються як невідомі.

`Changed` — час останньої зміни статусу у NovaPay. Його зберігаємо в UTC, відображаємо за Києвом із явним підписом «Статус»; це не окремо підтверджений час бухгалтерського проведення. Для контрагента зберігаються ім'я, рахунок і призначення; API CRM повертає лише маскований рахунок. Повторний імпорт не створює дублікатів; зміни зберігають історію.

Сторінка відкривається за поточний місяць з обома напрямами операцій. Перший імпорт можна обмежити початком місяця через `novapay_accounts.import_from`; відсутні дні автоматично добираються через чергу. Прив'язка до замовлень і автофіскалізація у цьому етапі не реалізовані.

Список повторює порядок колонок NovaPay: документ (`Code`, з початковими нулями), дата, відправник (`DebitName`, `DebitCodeIBAN`, `DebitStateCode`), сума, отримувач (`CreditName`, `CreditCodeIBAN`, `CreditStateCode`), статус і час його зміни. IBAN обох сторін маскується сервером. Надходження зелені, списання сині; призначення розкривається біля документа. Пошук працює також за номером документа та іменами обох сторін. Старі операції збагачуються повторним імпортом, а не створюються заново.

## Серверна черга

Задачі NovaPay використовують з'єднання `database` та окрему чергу `novapay`, незалежно від загального `QUEUE_CONNECTION`. Стандартний scheduler CRM щохвилини виконує `schedule:run`; оновлення балансу ставиться в чергу кожні 5 хвилин, повторна звірка — о 04:30 за Києвом.

Після першого штатного деплою встановіть `scripts/supervisor-domcrm-novapay.conf` у `/etc/supervisor/conf.d/domcrm-novapay.conf`, виконайте `supervisorctl reread` і `supervisorctl update domcrm-novapay`. Перевірка: `supervisorctl status domcrm-novapay:*`. Worker працює від `deploy`, слухає лише NovaPay та перезапускається після `queue:restart` у скрипті деплою. Його timeout 75 с менший за стандартний `database.retry_after=90` с.

Після підключення в CRM виберіть рахунок і ввімкніть оновлення. Стан задач доступний на вкладці синхронізації. Секрети не потрібно передавати через чат або комітити в Git.
