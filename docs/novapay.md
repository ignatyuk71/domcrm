# NovaPay: поточний етап

Сторінка `/finance/novapay` та всі її API доступні лише активному власнику. Реальні рахунки підключаються через логін бізнес-кабінету, Refresh Token і відкритий сертифікат API. Токени й сертифікат зберігаються зашифрованими ключем Laravel; ключ `APP_KEY` потрібно зберігати між релізами. Тестові підключення та демонстраційні дані на сервер не переносяться.

Баланс отримується окремо від виписки: доступний залишок не залежить від обраного періоду. Помилка оновлення зберігає попереднє значення й час його отримання. Суми обчислюються в цілих копійках.

Імпорт операцій вмикається через `NOVAPAY_OPERATIONS_VERIFIED=true`. Контракт `GetPaymentsList` перевірено на реальному рахунку 16.10.2026: список містить надходження та списання поточного дня, а також повну вибірку за 1–16 жовтня. Запит використовує `date_type=0`, окремі дні та весь XML-відгук без клієнтського обрізання. На кожен день зберігається стан повноти імпорту.

ID операції береться з елемента `ID`, дата — з `DayDate`; у проведених списань `PayDate` може бути порожньою. Перевірений статус `Conducted` відповідає «Проведено». Невідомі статуси, дубльовані ID, некоректні дати, чужий рахунок і непідтверджена структура зупиняють увесь імпорт дня. Надходження без повного покриття періоду відображаються як невідомі.

`Changed` — час останньої зміни статусу у NovaPay. Його зберігаємо в UTC, відображаємо за Києвом із явним підписом «Статус»; це не окремо підтверджений час бухгалтерського проведення. Для контрагента зберігаються ім'я, рахунок і призначення; API CRM повертає лише маскований рахунок. Повторний імпорт не створює дублікатів; зміни зберігають історію.

Сторінка відкривається за поточний місяць з обома напрямами операцій. Перший імпорт можна обмежити початком місяця через `novapay_accounts.import_from`; відсутні дні автоматично добираються через чергу. Зіставлення виплат із замовленнями описане нижче. Автофіскалізація не виконується.

Список повторює порядок колонок NovaPay: документ (`Code`, з початковими нулями), дата, відправник (`DebitName`, `DebitCodeIBAN`, `DebitStateCode`), сума, отримувач (`CreditName`, `CreditCodeIBAN`, `CreditStateCode`), статус і час його зміни. IBAN обох сторін маскується сервером. Надходження зелені, списання сині; призначення розкривається біля документа. Пошук працює також за номером документа та іменами обох сторін. Старі операції збагачуються повторним імпортом, а не створюються заново.

## Серверна черга

Задачі NovaPay використовують з'єднання `database` та окрему чергу `novapay`, незалежно від загального `QUEUE_CONNECTION`. Стандартний scheduler CRM щохвилини виконує `schedule:run`; оновлення балансу ставиться в чергу кожні 5 хвилин, повторна звірка — о 04:30 за Києвом.

Після першого штатного деплою встановіть `scripts/supervisor-domcrm-novapay.conf` у `/etc/supervisor/conf.d/domcrm-novapay.conf`, виконайте `supervisorctl reread` і `supervisorctl update domcrm-novapay`. Перевірка: `supervisorctl status domcrm-novapay:*`. Worker працює від `deploy`, слухає лише NovaPay та перезапускається після `queue:restart` у скрипті деплою. Його timeout 75 с менший за стандартний `database.retry_after=90` с.

Після підключення в CRM виберіть рахунок і ввімкніть оновлення. Стан задач доступний на вкладці синхронізації. Секрети не потрібно передавати через чат або комітити в Git.

## Виплати за замовленнями

`NOVAPAY_PAYOUTS_VERIFIED=true` вмикає джерело `payouts`: `GetRegister` (Type=1, CSV) формує реєстр підприємства, `DownloadRegister` повертає підписане посилання. ID звіту зберігається в задачі; наступна спроба використовує той самий ID. Завантаження дозволене лише через HTTPS зі сховища `storage.googleapis.com/prod-novaclients3-cod-statements/`, без перенаправлень і передачі JWT. CSV обмежений 10 MiB. Імена покупців, їх платіжні засоби та URL файлів у CRM не зберігаються.

Контракт перевірено 16.10.2026: CSV UTF-8 BOM, роздільник кома; ключ — «Унікальний обліковий номер фінансової операції», ТТН — «№ ЕН НП». Дата — «Дата перерахунку коштів», не дата отримання посилки чи оплати покупцем. Суми прийнятих коштів мінус винагорода повинні точно дорівнювати виплаті; розрахунки виконуються в копійках. Інші рахунки підприємства відфільтровуються за IBAN. Невідома структура, повторні ID, некоректні дати/суми блокують весь звіт. Повторний імпорт оновлює записи за стабільним ID; виправлення й відкликані рядки зберігають історію.

Група реєстру підтверджується лише за однозначного збігу з проведеним надходженням NovaPay на той самий рахунок: дата й точна сума групи, код відправника 38324133. Однакові суми кількох груп або банківських платежів залишаються непідтвердженими. Це звірка за реквізитами, а не переданий провайдером прямий зв'язок між ID реєстру й банківською операцією.

Замовлення зіставляється лише за точною поточною ТТН перевізника `nova_poshta`. Кілька замовлень із тією самою ТТН показуються як неоднозначні. Картка рахує унікальні замовлення з підтвердженими виплатами за датою виплати у вибраному періоді; без успішного покриття всього періоду показує «—». Список містить ТТН, замовлення, суми покупця/комісії/виплати та стан звірки. Дані реєстру можуть запізнюватись щодо банківських надходжень. Виплати є деталізацією вже наявних надходжень: нові записи `order_payments`, повторний дохід, зміни статусів і фіскальні чеки не створюються.

Перший імпорт починається з `import_from`, наступні оновлюють поточний і попередній день; щоденна звірка повторно отримує останні `reconcile_days`. Після тривалої паузи діапазон починається від останнього успішного звіту, щоб не залишити прогалин. Ручне «Оновити дані» також запускає реєстр. Доступ до даних та посилань замовлень залишається лише у власника.

Успішне отримання CSV означає завершення запиту, але не гарантує наявність деталізації всіх банківських надходжень. Проведені надходження від NovaPay без зв'язку з активними рядками реєстру повертаються окремо як `pending_incoming_count` / `pending_incoming_minor`. За наявності таких надходжень `paid_orders_count` залишається невідомим; `confirmed_paid_orders_count` містить лише вже підтверджені замовлення. Інтерфейс показує цю часткову кількість або «—», суму без деталізації та стан очікування, а не повідомляє про відсутність виплат. Після надходження й однозначної звірки реєстру стан очікування знімається автоматично. 16.10.2026 окремий запит реєстру за 16–17 жовтня також повернув порожній CSV за наявності проведених банківських надходжень за 16 жовтня; підтвердженого строку появи деталізації немає.

## Збої оновлення авторизації

JWT використовується до `exp` із запасом хвилина, максимум дві години; коротший строк провайдера має пріоритет. Попереднє обмеження чотирма хвилинами спричиняло зайві ротації майже кожне планове оновлення. Нова пара Refresh Token / сертифікат зберігається зашифрованою до першого запиту даних.

Таймаут (`auth_timeout`), мережевий збій (`auth_network`), HTTP-помилка з кодом статусу (`auth_provider_http`), неповна відповідь та відхилений результат більше не замінюються твердженням про необхідність нового токена. Безпечні код і текст зберігаються в підключенні та задачі; наступні вже поставлені задачі повторюють цю причину без нового HTTP-запиту. Сирі відповіді, винятки, URL і секрети не журналюються. Після невизначеної одноразової ротації автоматичні спроби призупиняються: невідомо, чи провайдер уже замінив попередню пару. HTTP 429 зберігає штатну повторну спробу. Збереження нових параметрів власником очищує стару діагностику; міграція лише додає порожні поля та не змінює токенів чи стану наявного підключення.
