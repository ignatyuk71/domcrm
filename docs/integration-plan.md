# План інтеграції зовнішніх сайтів з DOM-CRM

> Статус: **проєктування** (код ще не пишемо).
> Мета: замовлення з кількох зовнішніх сайтів автоматично потрапляють у CRM як `Order` + `OrderItem`, з коректним зіставленням товарів.

## 1. Обсяг (scope)

**Робимо:**
- Прийом замовлень: зовнішній сайт → CRM (одностороння синхронізація).
- Підтримка кількох сайтів одночасно через єдиний пайплайн.
- Два режими прийому: **PUSH** (webhook) і **PULL** (cron, для платформ без webhook).
- Зіставлення товарів через **пам'ять мапінгу** (різні коди на кожному сайті).

**НЕ робимо (свідомо викинуто для простоти й надійності):**
- Зворотну синхронізацію CRM → сайт (статуси, залишки, TTN назад на сайт).
- Авто-створення товарів у CRM з сайту (тільки мапінг на наявні + snapshot).

## 2. Архітектура

```
PUSH (webhook)                          PULL (cron кожні N хв)
┌──────────────┐ ┌─────────┐ ┌────────┐  ┌──────────┐
│ Власний PHP  │ │ Shopify │ │OpenCart│  │  Prom.ua │
└──────┬───────┘ └────┬────┘ └───┬────┘  └────┬─────┘
       │ canonical    │ webhook  │ webhook    │ pull API
       └──────┬───────┴──────────┘            │
              ↓                                ↓
    POST /api/v1/orders/intake      php artisan integrations:pull
              │                                │
              └────────────┬───────────────────┘
                           ↓
              external_orders_raw (сирий лог + ідемпотентність)
                           ↓
              Job: ProcessExternalOrder
                  ├─ Adapter.normalize()        ← свій на кожен type
                  ├─ Customer (phone_normalized) ← firstOrCreate
                  ├─ Items → мапінг по ПАМ'ЯТІ   ← external_products
                  │     └─ нема? snapshot + needs_review
                  ├─ OrderCreationService        ← спільний з ручним вводом
                  └─ raw.status = processed
```

**Принцип №1:** один **канонічний формат** усередині, багато **адаптерів** зовні. Новий сайт = новий адаптер, ядро не чіпаємо.

**Принцип №2:** приймаємо → зберігаємо сирий payload → відповідаємо `200 OK` → обробляємо в **черзі (Job)**. CRM на секунду лягла → замовлення не втрачене.

## 3. Ключове рішення: мапінг товарів (SKU-first + пам'ять)

> Оновлено: SKU можна зробити **однаковим скрізь** (сайт = CRM). Тоді SKU — основний авто-ключ, а ручний мапінг лишається лише для винятків. Це перевертає систему з «руками за замовчуванням» на «авто за замовчуванням».

Каскад із 3 ступенів:

```
item із сайту {external_id, sku, name, size, qty, price}
        │
  ┌─────┴───────┐
  │ 1. ПАМ'ЯТЬ    │ external_products (ручні правки/override + сайти без контролю SKU)
  │              │ → хіт? БЕРЕМО ✓   рішення оператора завжди головніше
  └─────┬────────┘
        │ нема
  ┌─────┴───────┐
  │ 2. SKU-AUTO   │ ProductVariant.sku = item.sku   (інакше Product.sku)
  │              │ → хіт? БЕРЕМО ✓   нові товари мапляться самі, 0 роботи
  └─────┬────────┘
        │ нема (SKU не заданий / не збігся / справді новий товар)
  ┌─────┴───────┐
  │ 3. SNAPSHOT   │ order_items зберігає назву/розмір/ціну з сайту,
  │ +NEEDS_REVIEW │ order.needs_review = true, product_id = NULL
  └──────────────┘ → оператор мапить 1 раз → external_products → далі авто
```

Чому пам'ять перша, а не SKU: якщо оператор колись свідомо виправив зіставлення (бо SKU був хибний), це виправлення має перемагати авто-збіг.

**Залізне правило:** замовлення ніколи не губиться через нерозпізнаний товар. Незіставлена позиція = snapshot + `needs_review`.

**Умови, щоб SKU-авто працював надійно:**
- **SKU на рівні варіанту — ПІДТВЕРДЖЕНО.** На сайті є батьківський SKU (`6027`) і варіантний (`6027-36-37`). Авто-ключ = варіантний SKU → `ProductVariant.sku`, влучає одразу в потрібний розмір (текст розміру парсити не треба). Батьківський `6027` — лише запасний.
- **SKU унікальний у CRM** (`product_variants.sku`) — інакше колізії й хибні зіставлення. Додати unique-індекс.
- **Фолбек лишається завжди.** SKU-first не прибирає страхувальну сітку (пам'ять + `needs_review`) — просто в неї потрапляє набагато менше позицій.
- **Не all-or-nothing.** Навіть частковий єдиний SKU дає виграш: ті товари йдуть авто, решта — через фолбек. Можна впроваджувати поступово.

**Два способи наповнити пам'ять:**
1. **Реактивно** — мапимо коли приходять замовлення. Перші дні нового сайту багато `needs_review`, далі затихає.
2. **Проактивно (рекомендовано на старті сайту)** — екран «Каталог сайту»: тягнемо список товарів сайту → оператор мапить весь каталог наперед → замовлення одразу чисті.

## 4. Адаптери (по одному на платформу)

| Платформа    | Режим | Адаптер          | Нюанс |
|--------------|-------|------------------|-------|
| Власний PHP  | PUSH  | `CustomAdapter`  | passthrough — сайт шле наш canonical формат, мінімум роботи |
| Shopify      | PUSH  | `ShopifyAdapter` | стандартний webhook, мапимо їхній JSON |
| OpenCart     | PUSH  | `OpenCartAdapter`| треба модуль на сайті, що шле webhook |
| Prom.ua      | PULL  | `PromAdapter`    | cron тягне через Prom API, webhook немає |

Кожен адаптер = один метод `normalize($raw): CanonicalOrder`. Решта пайплайну однакова.

## 5. Canonical формат (внутрішній стандарт)

```json
{
  "external_order_id": "1234",
  "customer": { "first_name": "", "last_name": "", "phone": "", "email": "" },
  "items": [
    { "external_id": "584", "name": "Тапочки 39", "size": "39", "qty": 1, "price": 380 }
  ],
  "delivery": {
    "type": "nova_poshta_warehouse",
    "city_name": "Київ",
    "warehouse_name": "Відділення №42",
    "recipient_name": "",
    "recipient_phone": ""
  },
  "payment": { "method": "cod", "total": 380 },
  "note": ""
}
```

Місто/відділення передаємо **текстом**, не реф-ID. Резолв у довідник Нової Пошти — окремо, через наявний `NovaPoshtaService` (див. відкрите питання №2).

## 6. Прив'язка до існуючого коду

Що вже є і використовуємо:

- `OrderItem.product_id` — **nullable**, + снапшоти `product_title / sku / size / color`. Готово для `needs_review` без змін.
- `OrderItem.product_variant_id` — мапінг до рівня варіанту (розмір).
- `Customer::firstOrCreate(['phone' => ...])` у `OrderController.store()` — основа дедуплікації клієнтів.
- `OrderSource` (таблиця `order_sources`) — вже наявний реєстр каналів (`code/name/type/...`).
- `NovaPoshtaService`, `CheckboxService` — наявні зовнішні сервіси; інтеграція їх не дублює.
- `routes/api.php` — порожній; Sanctum **не встановлено** → API-автентифікацію додаємо у Фазі 1.

## 7. Зміни в схемі БД

**Нові таблиці:**

`external_orders_raw` — сирий лог + ідемпотентність
- `source_id` (FK), `external_order_id` (string)
- `payload` (json), `status` (received/processing/processed/failed), `error` (text null)
- `order_id` (FK orders, null — заповнюється після обробки)
- `received_at`, `processed_at`
- **UNIQUE (source_id, external_order_id)** ← захист від дублів

`external_products` — пам'ять мапінгу
- `source_id` (FK), `external_id` (string), `external_size` (string null), `external_name` (string, для оператора)
- `product_id` (FK null), `product_variant_id` (FK null)
- **UNIQUE (source_id, external_id, external_size)**

**Зміни наявних таблиць:**

- `orders`: `external_id` (string null, index), `needs_review` (bool, default false). UNIQUE для ідемпотентності — `(source_id, external_id)`.
- `order_items`: `external_id` (string null) — щоб з екрана замовлення знати, який зовнішній товар мапити. (Статус «не зіставлено» = `product_id IS NULL`, окреме поле не обов'язкове.)
- `customers`: `phone_normalized` (string, index) — для надійної дедуплікації.
- Канали інтеграції — **розширити `order_sources`** (рекомендовано) полями `mode` (push/pull), `adapter_type`, `api_key` (hash), `hmac_secret`, `pull_config` (json), `last_pulled_at`. Альтернатива — окрема `external_sources` (див. відкрите питання №1).

## 8. Фази впровадження

**Фаза 1 — Фундамент (база + прийом)**
- Міграції з розділу 7.
- `OrderCreationService` — винести логіку зі `store()` контролера (спільний код ручного й авто-вводу).
- `phone_normalized` + нормалізатор телефонів.
- `POST /api/v1/orders/intake` + middleware `VerifyExternalSource` (API-key + HMAC).
- `CustomAdapter` (passthrough).
- **Результат:** один самописний сайт уже шле замовлення в CRM.

**Фаза 2 — Мапінг (серце)**
- 2-ступеневий каскад (пам'ять → snapshot + review).
- Екран «Незмаплені позиції» — оператор домаплює.
- Екран «Каталог сайту» — проактивний мапінг наперед.
- **Результат:** товари з різними кодами коректно стають товарами CRM.

**Фаза 3 — Платформи**
- `ShopifyAdapter` + `OpenCartAdapter` (PUSH).
- `PromAdapter` + cron `integrations:pull` (PULL).
- Документація для розробників сайтів (як підключитися).
- **Результат:** усі сайти підключені.

**Фаза 4 — Надійність**
- Алерти (Telegram/email) при помилці обробки чи невідомому товарі.
- Rate-limit, повторні спроби job.
- Тестовий endpoint `/api/v1/orders/test`.

## 9. Відкриті питання (вирішити перед кодом)

1. **`order_sources` vs нова `external_sources`?** У коді вже є реєстр каналів. Рекомендація — розширити `order_sources`, щоб «Сайт X» був одним об'єктом і для відображення, і для інтеграції. Підтвердити.
2. **Резолв Нової Пошти з тексту** — як перетворити `city_name`/`warehouse_name` у реф НП через `NovaPoshtaService`? Точність пошуку? Що при неоднозначності → теж `needs_review`?
3. **Валюта** — `Order.currency` сьогодні UAH/PLN. Shopify/Prom можуть давати інше. Мапінг/заборона?
4. **Справді новий товар** (якого нема в CRM взагалі, а не просто не змаплений) — лишаємо snapshot чи даємо оператору створити `Product` прямо з екрана мапінгу?
5. **Стабільність `external_order_id`** на кожній платформі (ключ ідемпотентності) — підтвердити, що не змінюється.
6. **Авто-замовлення одразу «в роботу» чи через апрув?** Чи потрібен статус-буфер перед тим, як замовлення стає бойовим.
7. **Керування єдиним SKU.** ✅ Підтверджено: варіантний SKU контрольований на всіх платформах, включно з Prom (можна вставляти потрібний SKU). Перевірити при `PromAdapter`: чи Prom-API *повертає* варіантний SKU у позиціях замовлення. Лишається відкритим: хто стежить за однаковістю SKU при нових товарах/перейменуваннях; чи вже вирівняний наявний каталог.
